# DualBoost Bond protocol, version 1

The phone keeps several TCP connections ("subflows") to the bond server — some over Wi-Fi,
some over mobile data. All of them belong to one **session**. Every app connection becomes a
**flow** inside the session; its bytes are cut into chunks and each chunk travels over whichever
subflow will deliver it soonest. The other side puts the chunks back in order. A single app
connection therefore uses both links at once, and survives one link dying.

## 1. Transport (per subflow)

Pre-shared key `K` (32 random bytes, generated by the app, given to the server by the setup script).

```
C → S   "DBB1" (4)  clientNonce (32)
S → C   serverNonce (32)
prk   = HMAC-SHA256(K, "dualboost v1" | clientNonce | serverNonce)
k_c2s = HMAC-SHA256(prk, "c2s")        k_s2c = HMAC-SHA256(prk, "s2c")      (AES-256 keys)
```
After that every message is a **record**: `len u16 BE | AES-256-GCM(ciphertext + 16-byte tag)`.
Nonce = 12-byte big-endian counter, starting at 0, per direction. Fresh nonces from both sides
make every subflow's keys unique (no replay). A wrong key fails the first record; the server
then closes silently. Each record holds exactly one **frame**: `type u8 | payload`.
Max plaintext 16 400 bytes. All integers big-endian.

## 2. Frames

| type | name | payload | scope |
|---|---|---|---|
| 0x01 | HELLO | sessionId(16) link u8 (1 Wi-Fi, 2 mobile) subId u8 standby u8 | first C→S record |
| 0x02 | WELCOME | status u8 (0 new session, 1 resumed) version u8 | first S→C record |
| 0x10 | OPEN | flow u32, proto u8 (1 TCP, 2 UDP, 3 speed-down, 4 speed-up), atyp u8 (1 IPv4, 4 IPv6, 3 name: len u8 + bytes), addr, port u16, window u32 | session |
| 0x12 | DATA | flow u32, seq u64, bytes | session |
| 0x13 | ACK | flow u32, next u64 (first byte still missing), limit u64 | session |
| 0x14 | FIN | flow u32, final u64 | session |
| 0x15 | RST | flow u32, code u8 | session |
| 0x16 | DGRAM | flow u32, id u32, bytes | session (never resent) |
| 0x20 | PING | id u32, t u64 | subflow |
| 0x21 | PONG | (copy of PING payload) | subflow |
| 0x22 | SUBACK | received u64 = record bytes (incl. length header) received on this subflow | subflow |
| 0x23 | GONE | subId u8 | session, sent when a subflow died |
| 0x24 | STANDBY | standby u8 | subflow (C→S) |

Flow ids are chosen by the phone (only the phone opens flows). RST codes: 1 refused,
2 unreachable, 3 timeout, 4 name not found, 5 reset by peer, 6 not allowed, 7 closed.

## 3. Reliability: per-subflow log

Subflows are TCP, so a record is lost only if its subflow dies. Every **session** frame
(OPEN, DATA, ACK, FIN, RST) a sender writes is kept in that subflow's log with its end offset
(record bytes written so far). The receiver reports `SUBACK received`; log entries with
end ≤ received are dropped. When a subflow dies, every entry still in its log is sent again,
in order, on a live subflow. All session frames are idempotent: DATA is deduplicated by seq,
OPEN of a known flow is ignored, FIN/RST/ACK are safe to repeat. Frames for a flow that was
already closed are ignored. DATA/FIN that arrive before their OPEN are held until it arrives.

SUBACK is sent only for received bytes other than SUBACKs (never confirm a confirmation):
within 10 ms for session frames and datagrams, lazily (1 s busy, 5 s idle) for pings/pongs.
PING runs every 250 ms on both sides while data flows; when idle only the phone pings, every
5 s. A subflow is dead when its socket fails, or when nothing has been received on it for
2.5 s while busy (12 s idle). While busy, a subflow silent for 0.7 s while another is talking
becomes *suspect*: it gets no new data and its unconfirmed frames are copied to others. The detecting side sends GONE on a live subflow so the
other side resends its log for that subflow immediately.

## 4. Flow control

Each flow direction has a window. OPEN carries the phone's first receive window (2 MiB); it
grows up to 16 MiB per flow, but the phone never promises more than 64 MiB over all flows
together (each flow keeps at least 256 KiB). The server's window is 4 MiB. The receiver sends `ACK next limit`: `next` is the first byte it is still missing, and the sender may send bytes up to `limit`. While data is out of order, ACK repeats every 20 ms. When a sender is window-blocked and the missing chunk sits on a clearly slower subflow, it sends copies of it (and the chunks after it there) over a faster subflow (opportunistic resend).
Buffered (in-order + out-of-order) data never exceeds the window. ACK is sent when consumption
advanced by a quarter of the window, at most every 20 ms, and again for every flow after a GONE.

## 5. Scheduling (sender side, both directions)

Per subflow: `inflight = written − subacked`, `rate` (EWMA of SUBACK progress while busy),
`minRtt` (lowest PING RTT in the last 10 s). Estimated arrival of the next chunk on subflow s:
`est(s) = (inflight(s) + chunk) / rate(s) + minRtt(s) / 2`.
A ready subflow writer takes the next frame only if `est(s) ≤ 1.2 · min est + 2 ms` over all
usable subflows, and its inflight is below `max(4 · rate · minRtt, 256 KiB)`. Standby subflows
(Backup mode, data limit, or the "combining is slower" verdict) are used only when no
non-standby subflow is alive. Datagrams go to the subflow with the lowest est; DNS goes once
per link (deduplicated by id). Datagrams wait in a per-subflow queue of at most 256 KiB
(oldest dropped), are dropped after 200 ms, respect the inflight cap, and are never resent.
A datagram larger than 16 391 bytes is dropped.

## 6. Sessions

A session lives while it has subflows, and for 120 s after the last one is gone. WELCOME status
0 on a session the phone thought was alive means the server restarted: the phone resets all
flows and starts a new session id.

## 7. Limits

Server: at most 256 unauthenticated handshakes at once (16 per address, 4 s each), 16 sessions,
16 subflows per session, 8192 flows per session (beyond that, OPEN gets RST 6). Flows may not
reach loopback, private, link-local, CGNAT, reserved ranges or the server's own addresses.

## 8. Speed flows

proto 3: the server sends an endless zero stream (flow-controlled) until the phone sends RST.
proto 4: the server reads and discards; its ACKs show the upload rate.
